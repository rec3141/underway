# Underway dashboard review — 4 September 2026

Reviewed commit `5d838a1535a8f1a1beb75319f1447efd1080bc62`, the running workstation configuration, local mirrored data, and a limited selection of shared-drive directories. This was a review: application code, services, routing, and source data were not changed.

The architecture already fits shipboard use well: bundled JavaScript and geography, a local mirror, incremental SQLite ingestion, per-file atomic publication, bounded chat history, and optional-feature error handling. A sampled production build completed successfully in about 22 seconds with 2,779,084 observations across eight legs. The main gaps are installation reproducibility, recovery after disconnections, and keeping all tabs synchronized.

## Why one user might only reach the Wi-Fi URL

The workstation has two separate physical network connections:

| URL | Interface / behavior |
| --- | --- |
| `http://192.168.3.216/underway/` | Wi-Fi, `wlo1`, `192.168.3.0/24` |
| `http://10.0.0.58/underway/` | Ethernet, `enp6s0`, `10.0.0.0/24` |
| `http://underway.local/` | mDNS name; direct dashboard virtual host |

Both IP roots redirect to `/underway/`. All three manifest URLs returned HTTP 200 from the workstation. That confirms local service behavior, not reachability from another client's network.

A Wi-Fi client may reach the Wi-Fi address but lack access to the wired subnet. The hostname adds an independent dependency on multicast name discovery and the client's resolver. The publishing script currently advertises both IPs without tying each advertisement to its owning interface; inspect the affected client's actual resolution result before attributing failure to mDNS support.

There is also a definite server-side routing wrinkle: `ip route get 10.0.0.172` selects `tun0`, while `ip route get 10.0.0.10` correctly selects Ethernet. The VPN's host-specific /32 route beats the helper's /26 routes. A wired client using an overridden address can therefore have replies sent toward the university VPN. This is a possible explanation, not confirmation of that user's case.

Useful next observations from the affected device: IP address/subnet, Wi-Fi network, VPN state, the address returned for `underway.local`, and whether the failure is name resolution, connection timeout, or a partially loaded page. Keep the explicit Wi-Fi HTTP URL available as a fallback. Ship DNS plus reserved addresses would provide a more predictable long-term entry point than mDNS alone.

## Additional reliability and portability feedback

- **Keep last-good data through incomplete source discovery.** `ingest.sync()` drops files missing from the discovered set. A directory becoming unavailable between leg discovery and ingestion, or a partially missing input set, can remove previously cached observations. Whole-leg disappearance also removes that leg from the next published manifest. The non-deleting mirror reduces this risk, but direct-share mode needs a distinction between unavailable inputs and deliberate retractions.
- **Bound mirror/build duration and expose source health.** The builder service currently reports `TimeoutStartUSec=infinity`. An rsync protocol timeout does not guarantee a CIFS filesystem call returns, so a stalled run can hold the build lock indefinitely. Report last successful mirror and build separately; retain cached data with a visible stale state. The mirror script logs failures but does not consistently return a failure status.
- **Publish one coherent generation.** Each JSON file is atomic, but all windows are overwritten before the manifest. A reader can pair an old manifest with a new window (especially problematic if leg indices change), and a failed build can leave mixed generations. Generation-specific data filenames/directories, published by a final manifest swap, would make the existing atomic approach complete.
- **Make runtime caches crash-tolerant.** TSG pickle, schedule/history, and Google Calendar queue/state files use direct writes. Some reads happen outside recovery handlers; a truncated TSG cache disables flow input on subsequent builds, and a truncated schedule cache can prevent recovery on later runs. Use atomic replacement, validate reads, and rebuild disposable caches. Calendar state deserves stronger preservation because it tracks external effects. Keep pickle caches on trusted local storage.
- **Finish cross-platform defaults.** Use explicit UTF-8 for generated text. Default caches to a writable user-data directory, not an installed package's parent, and avoid `/data/...` as the only usable chat default. Document environment overrides. Shell wrappers/systemd files are Linux/ship-specific, hard-code Miniforge and workstation paths, and should be clearly separated from portable Python instructions. Declare `xlrd` for the current Excel logs and optional requests/PyJWT dependencies. Update the README's timer cadence and surprise-model description to match the current implementation.
- **Keep HTTP requests bounded.** POST lengths should reject negative/oversized values rather than relying on `min(length, 4096)`; negative lengths can become an unbounded read. Add request timeouts. A bounded work queue for AI replies would prevent multiple `@crew` requests from accumulating threads behind one inference lock. These are modest stability measures; viewing need not require accounts.
- **Escape source-derived HTML.** Most chat/template output is escaped, but provenance/source strings are interpolated into `innerHTML` in `app.js`. Use text nodes or a consistent escaping helper for shared-data headers and notes. This was identified by inspection, not tested with malicious shared files.

## Device checks

A fresh headless Chromium profile loaded the deployed dashboard at 390×844 and 1440×900. Underway, Casts, Agenda, and Table were exercised. The phone-width underway screen created 17 Plotly plots, including the map, and no uncaught JavaScript exceptions were recorded. This is a browser smoke check, not physical iOS/Android or Safari validation.

Agenda content exceeded the 390-pixel viewport (body scroll width 470 pixels); the overflowing element was `table.sched`. Casts/Table were about two pixels over. Give the schedule table a narrow-screen layout or its own horizontal scrolling region. Other useful follow-ups are keyboard tab behavior, touch scrolling over charts, software-rendered/WebGL-unavailable devices, browser sleep/resume, and long-lived sessions with repeated updates. The error handler currently suppresses Plotly-related promise errors, so a map failure could be difficult to diagnose. Provide an explicit map-unavailable message while keeping tables and plots usable.

The bundled Plotly file is about 4.7 MB and vector geography totals about 4.9 MB before compression. Caddy enables compression; direct port 8042 uses the Python server without it. Keep Caddy's port-80 entry points as the documented path. Consider a lighter first load and deferring unused map layers, particularly when raster relief is present.

## Enhancement opportunities

Tracked in [#10](https://github.com/rec3141/underway/issues/10).

1. **Make data quality visible.** Surface intake-flow status, last valid sample, missing fraction, and selected source beside each variable. The existing flow gate already protects surprise scoring; expose that context on TSG plots and downloads too. Separate acquisition age from page/build age.
2. **Connect existing observations.** Link the underway cursor, casts, and event log; add a temperature–salinity comparison using existing profiles and surface measurements. Preserve units, quality flags, and provenance in exports. These features use established inputs and require no new share scan.
3. **Add barge CTD profiles.** A sampled `Data/Barge_CTD/` CSV lists time, position, conductivity, temperature, pressure, salinity, and depth. It looks like a practical addition to the existing Casts UI once units and cast boundaries are confirmed.
4. **Investigate Hydrobios.** Leg directories and a header template are present. Profile parsing and station matching need investigation before estimating the work.
5. **Explore camera context selectively.** All-sky and 360-camera directories exist. Image availability, timestamps, and sharing suitability were not verified. If appropriate, small on-demand thumbnails could add cloud/ice context without burdening every page load.
6. **Treat PySAS and AIS as follow-up projects.** PySAS has current raw files and requires format/calibration knowledge for scientific display. AIS logs exist, but freshness was not established—the sampled filename was from 2023. Do not advertise a live AIS layer until current coverage is confirmed.

The first two enhancements offer the most immediate value with the least additional ingestion and operational work.
